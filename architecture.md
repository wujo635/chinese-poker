# Architecture

## Overview
Chinese Poker (十三水) MVP — a React + TypeScript + Vite single-page app. Game logic is built as a pure, framework-free "engine" layer, with React components consuming it. This separation keeps the trickiest code (hand ranking, comparison, validation, scoring) independently testable without any UI concerns.

## Stack
- **Build tool**: Vite
- **UI**: React 19 + TypeScript
- **Testing**: Vitest + React Testing Library (jsdom environment)
- **Linting**: oxlint
- **Persistence**: browser `localStorage` (no backend)
- **Deploy target**: GitHub Pages (static build, `base: '/chinese-poker/'` in `vite.config.ts`), auto-deployed via `.github/workflows/deploy.yml` on push to `main`

## Engine Layer
Pure functions with no side effects, unit-tested independently of the UI (`src/engine/__tests__/`):
- `deck.ts` — deck creation, shuffling, dealing, card comparison. Ace is 14 by default.
- `handRank.ts` — `getHandStrength()` returns a comparable `[category, ...tiebreakers]` tuple (not just a 1-10 number) so same-category hands compare correctly by kicker. Straight detection special-cases the A-2-3-4-5 wheel. **Straight ranking is a house rule, not standard poker order (v0.19.1)**: broadway (A-K-Q-J-10) > wheel (A-2-3-4-5) > every other straight (6-high through K-high). `straightInfo()` returns `{ rankHigh, displayHigh }` — `rankHigh` feeds the comparison tuple (wheel = `13.5`, strictly between K-high's 13 and broadway's 14), while `displayHigh` stays the wheel's actual high card (5) and is used only for Royal Flush detection/labeling, so the wheel still displays as a plain "Straight." Royal Flush is category 9 internally (same as Straight Flush) — `identifyHandType()` only distinguishes it for display naming, since an Ace-high straight flush already outranks others via the tiebreaker. **3-card front hands only ever reach High Card / Pair / Three of a Kind** — straights/flushes are not scored at 3 cards, per standard Chinese Poker rules.
- `compareHands.ts` — compares two same-size hands via their strength tuples; falls back to a suit tiebreaker (♠>♥>♣>♦) on each hand's highest card if the rank strength is exactly equal.
- `validate.ts` — `validateArrangement()` requires **strict** back > middle > front; an exact tie between two rows is a foul.
- `game.ts` — game/round orchestration. **Dealer-only scoring (v0.14.0)**: `resolveRound()` compares the Dealer's hand against every other player's hand independently — non-dealer players never score against each other. `GameState.dealerId` identifies the Dealer seat; `initializeGame({ seats, dealerIndex })` builds `players` from an explicit seat-type list and sets `dealerId` accordingly (this replaced the old `initializeGame(playerNames: string[])`, which hard-coded the first name as the sole human). `GameState.results` holds one `RoundResult` per (player, opponent) pairing rather than one per player — a player's total round score is the sum of their entries (always one entry for a non-dealer, one per opponent for the Dealer). Each `RoundResult` carries an explicit `opponentId` (added in v0.6.0) so the UI can look up "my result against this specific opponent" without relying on array ordering. `normalizeLegacyGameState()` defaults `dealerId` to `players[0]` for saves persisted before this field existed. A fouled player auto-loses -3 against every valid opponent (changed from -6 in v0.11.0); two fouled players tie 0 against each other. **Per-hand scoring (v0.10.0)**: each of front/middle/back is scored independently, and the winner's point value depends on the *winning* hand's category on a zone-specific scale (not a flat ±1) — see `frontPoints()`/`middlePoints()`/`backPoints()`. Front: Three of a Kind = 3, anything else = 1. Middle: Straight/Royal Flush = 10, Four of a Kind = 8, Full House = 2, anything else = 1. Back: Straight/Royal Flush = 5, Four of a Kind = 4, anything else = 1. There is no scoop bonus — a round score is just the sum of the three zone scores. Ties score 0. Foul penalty is a flat -3 against every valid opponent.
- `ai.ts` — `generateAIArrangement()`: brute-force strongest 5-card back, then strongest 5-card middle from the remainder, leftover 3 cards become front. Can theoretically foul on rare/weak hands (acceptable for MVP per spec). **"Maximizer" strategy** (v0.18.0 naming) — no longer called from any production path as of v0.21.1; kept only as the baseline `ai.test.ts` benchmarks the Optimal strategy against. `generateOptimalArrangement()` (v0.18.0, tie-break refined v0.19.1/v0.20.2) — brute-forces every valid (front, middle, back) partition of the 13-card hand and picks the one maximizing total zone points from the real scoring table (`frontPoints`/`middlePoints`/`backPoints`, imported from `game.ts`), rather than greedily maximizing the back hand alone; prefers a non-fouling arrangement, falling back to the highest-scoring overall only if every partition fouls. It's a globally optimal maximizer, not a distinct "personality" — mathematically guaranteed to place a strong hand in whichever legal zone pays more. Ties on formal score are broken by raw category-sum (v0.19.1), then by full hand-strength tuples in front→middle→back priority (v0.20.2, `isBetterPartition()`) so a materially stronger option (e.g. the highest of several tied pairs) lands in front deterministically. **Used by every AI-controlled seat (v0.21.0) and the human's "Auto-Place" button (v0.21.1)** — there is no longer a Maximizer/Optimal split by seat.
- `autoWin.ts` (v0.22.0) — Automatic Winning Hands. `detectAutoWin(hand: Card[])` classifies a raw 13-card deal (independent of arrangement) as one of 6 types, checked in priority order: Dragon (13 points; one card of every rank 2-A) > Six Pairs (3 points) > Four Pairs + Flush (3) > Four Pairs + Straight (3) > Three Flushes (3) > Three Straights (3), or `null`. Six Pairs and the Four-Pairs variants are `O(13)` rank-count-pattern checks (reuses `rankCounts`, exported from `handRank.ts` for this). Three Flushes checks all suit-assignment combinations for the 3/5/5 zone sizes (~64 combos) and requires exact per-suit demand-vs-count equality. Three Straights searches over rank-value *windows* rather than brute-forcing all 72,072 card partitions (`generateOptimalArrangement`'s cost class, ~150-300ms — too slow to run for every player every deal): only 11×9×9 = 891 window combinations, each an O(13) demand-vs-count check across the full 2-14 rank domain, making it sub-millisecond. `game.ts`'s `scorePairwise` checks both players' auto-win status (only counted if that player's own arrangement is valid) before the normal foul-handling branches, so a valid auto-win short-circuits past the opponent's foul status entirely and replaces normal front/middle/back scoring outright; same-tier auto-wins (including two of the same type, or two Dragons) wash at 0. `RoundResult`/`Player`/`GameState` are intentionally unchanged — `ResultsScreen` derives the display badge by calling `detectAutoWin(player.hand)` directly wherever a player is already in scope, gated on `isValid`.
- `persistence.ts` — `saveGameState`/`loadGameState`/`clearGameState` keyed by `gameId` under a `chinese-poker:game:` localStorage prefix; `listSavedGameIds()` scans that prefix for a "load saved game" screen. `loadGameState` returns `null` (not a throw) on missing or corrupted data.
- `leaderboard.ts` (v0.17.0) — a persisted, all-time high-score board, independent of `persistence.ts`'s per-game saves. `loadLeaderboard()`/`recordScore(mode, score, seatCount)` store a single JSON blob under a fixed `chinese-poker:leaderboard` key (`Record<'dealer' | 'player', LeaderboardEntry[]>`), mirroring `persistence.ts`'s no-versioning, try/catch-on-corrupt conventions. `recordScore` appends an entry, sorts descending, and truncates to the top 5 per mode.
- `arrangementMoves.ts` (v0.20.0) — pure, dnd-kit-independent state transitions for `ArrangementScreen`'s in-progress hand: `moveCardToHand`, `moveCardToZoneSlot`, `swapCards` (all keyed by `cardKey`, not array index — zone/hand order has no game-logic meaning), and `computeDragEndResult()`, which dispatches a drag-end event (duck-typed against dnd-kit's `DragEndEvent` shape) to the right helper based on the drop target's id namespace. Also owns the `ArrangementState`/`ZoneName`/`ZONE_CAPACITY`/`cardKey` definitions, moved here from `ArrangementScreen.tsx` (which re-exports `ArrangementState` for backward compatibility). Both the click-based and drag-based interaction paths in `ArrangementScreen.tsx` call these same functions, so they're provably doing identical state transitions.

- **v0.20.2**: Fixed a remaining gap in `generateOptimalArrangement`'s tie-breaking (the AI Dealer's strategy in Player mode, added v0.18.0, previously refined in v0.19.1). The v0.19.1 fix broke ties on raw category-sum, but categories don't distinguish rank — e.g. any pair scores category 2 regardless of whether it's a pair of Aces or a pair of 2s, so when a hand offers several same-category options (classic case: three pairs splittable between front and middle), the search could arbitrarily leave any one of them in front. Added a further tie-break, `isBetterPartition()`, that compares full hand-strength tuples in front → middle → back priority once total score and category-sum both tie, so the search now deterministically prefers the strongest available card ranks in front — e.g. the highest of several tied pairs. Verified with a new `ai.test.ts` case: a hand with a fixed unbeatable Four of a Kind in back plus three pairs (Aces/Kings/Queens) splittable between front and a middle two-pair, where every split ties on both total score and category-sum, asserts the Aces land in front.

- **v0.21.0**: Every AI-controlled seat now uses `generateOptimalArrangement`, not just the AI Dealer. Previously `App.tsx`'s `dealWithAiArrangements` branched — the dealer got the Optimal strategy, non-dealer bots got the older greedy `generateAIArrangement` Maximizer — but there was no real justification for two AI tiers once Optimal existed and wasn't prohibitively expensive. The branch is removed; every `player.type === 'ai'` takes the same `generateOptimalArrangement` path regardless of seat. `generateAIArrangement` (Maximizer) is unremoved — it still backs the human's "Auto-Place" button and the Maximizer-vs-Optimal comparison tests in `ai.test.ts`. Tradeoff accepted knowingly: "New Game"/"Play Again" now runs the brute-force search for up to 3 AI seats sequentially instead of 1, measured at roughly 1 second of synchronous blocking in a dev build before the arranging screen renders (verified via `performance.now()` around the click handler in a real browser) — judged an acceptable one-time cost for uniformly stronger AI play; not addressed with async/worker scheduling here. Verified end-to-end in a real browser: a full Dealer-mode round with all 3 bots completes with no fouls on any AI seat.

- **v0.21.1**: The human's "Auto-Place" button (`ArrangementScreen.tsx`'s `handleAutoPlace`) switched from `generateAIArrangement` to `generateOptimalArrangement`, matching every AI-controlled seat (unified in v0.21.0) — no reason for the human's manual auto-arrange to be weaker than the AI opponents it's compared against. `generateAIArrangement` (the greedy Maximizer) is no longer called from any production code path; it remains solely as the baseline `ai.test.ts` benchmarks Optimal against. Verified end-to-end in a real browser: Auto-Place completes in ~300ms (single-seat cost, unlike the ~1s multi-seat "New Game" cost from v0.21.0) and produces a non-fouling, correctly-optimized arrangement (Full House in back, Flush in middle).

- **v0.21.2**: Fixed a CI build failure (see `notes/build failure 2026-08-10.txt`) surfaced by v0.21.0/v0.21.1's AI-unification: `npm run test:ci` failed on GitHub Actions with 3 timed-out `App.test.tsx` tests, all of which play two full rounds (New Game/Play Again x2) and hit Vitest's default 5000ms `testTimeout`. With every AI seat and Auto-Place now running `generateOptimalArrangement`'s brute-force search, a 2-round Player-mode session computes it up to 6 times (up to 3 AI seats x 2 rounds), which the CI runner couldn't finish inside 5s. Fixed by raising `testTimeout` to 15000ms globally in `vite.config.ts`'s `test` block, rather than patching just the 3 failing tests — several *single*-round tests were already passing at 2.5-4.6s locally (visible in the same CI log), close enough to the old ceiling to be a latent CI flakiness risk even though they hadn't failed yet. No test logic changed, no production code changed.

- **v0.22.0**: Automatic Winning Hands — the last item on the post-MVP backlog. New `autoWin.ts` module (see Engine Layer above) detects 6 special 13-card deals (Dragon, Six Pairs, Four Pairs + Flush, Four Pairs + Straight, Three Flushes, Three Straights) from a player's raw hand and, when the player's own arrangement is valid, replaces normal front/middle/back scoring against each opponent with a fixed bonus (13 for Dragon, 3 for every other type). Dragon beats every other type; same-tier auto-wins wash. No UI flow changes — players still go through normal arrangement; `ResultsScreen` shows a badge next to the qualifying player's name (matchup rows and hand-reveal header), derived live via `detectAutoWin(player.hand)` rather than any new field on `RoundResult`/`Player`/`GameState`. Verified via `autoWin.test.ts` (10 cases covering each type, a regression case for the caught bug, and a priority-order case), 7 new `resolveRound` cases in `game.test.ts`, 2 new `ResultsScreen.test.tsx` cases, and a real-browser playthrough confirming a normal (non-auto-win) round still scores and renders correctly with no console errors.
